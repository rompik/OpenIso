## Как вести спецификацию

- Требования описывают ожидаемое поведение программы, а не автоматически повторяют текущее состояние кода.
- Пишите пользовательское поведение ясным языком; детали реализации и проверяемые критерии добавляйте в тот же тематический документ, не дублируя их в других разделах.
- Заполняйте заготовки по мере появления согласованных требований. Неизвестные правила и спорные сценарии оставляйте открытыми до решения владельца продукта.
- Русская версия является источником истины. Переводы ведутся в GitHub через pull request и должны соответствовать русскому оригиналу.
- Обновляйте затронутую спецификацию вместе с изменением поведения программы. Обновляйте пользовательские инструкции, если изменились шаги, элементы интерфейса или результат для пользователя.
- Спецификация описывает целевое поведение ветки разработки и не привязывается к номеру версии в каждом файле. Для исторических состояний используйте Git-теги и релизные заметки; файл `VERSION` меняйте только при отдельном решении о выпуске.
- Раздел 8 задаёт модель символа и персистентности; разделы 9 и далее определяют преобразования, проверки и этапы внедрения. Сверяйте реализацию с утверждёнными требованиями, а не наоборот.
- Машинно-проверяемые JSON Schema и их примеры хранятся в `docs/specification/schemas/`; требования к их смыслу и преобразованиям находятся в тематических русских разделах.

## Пользовательские руководства

Существующие руководства остаются в `docs/ru/` и `docs/en/`, чтобы сохранить текущие ссылки и упаковку. Они объясняют практические действия в приложении; спецификация фиксирует ожидаемое поведение. Не копируйте в руководство внутренние детали БД, если они не нужны пользователю.

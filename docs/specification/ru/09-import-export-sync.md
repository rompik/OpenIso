# 9. Импорт, экспорт и синхронизация

## 9.1 Источники и роли форматов

`OpenIso.json` является единственным эталонным каталогом символов. SQLite содержит рабочее представление каталога и состояние приложения; локальные изменения не должны автоматически перезаписывать эталонный JSON. Перенос локального изменения в каталог выполняется как отдельное согласованное изменение.

Форматы имеют следующие роли:

| Формат | Роль |
| --- | --- |
| `OpenIso.json` | Эталонный каталог. Каждая запись содержит код и атрибуты базового символа. |
| `OpenIso.Canonical` | Версионируемый нейтральный JSON-формат обмена между импортёрами, экспортёрами, каталогом и локальным хранилищем. Это представление для преобразования, а не второй редактируемый источник истины. |
| `OpenIso.Symbol.HR` | Человекочитаемый входной формат для проектирования, ревью и импорта символа в эталонный каталог. Изменения в нём не становятся эталонными до импорта и проверки. |
| `openiso-ois` | Формат экспорта/резервной копии локального состояния. Файл OIS не является источником эталонных определений. |
| ASCII и IDF | Поддерживаемые legacy-форматы импорта и экспорта. |

JSON Schema и примеры форматов хранятся в `docs/specification/schemas/` и проверяются тестами. Русские разделы 8–9 определяют смысл и правила преобразования; схемы форматов задают машинно-проверяемую структуру.

## 9.2 Canonical JSON

Документ Canonical имеет поля верхнего уровня:

| Поле | Назначение |
| --- | --- |
| `format` | Строка `OpenIso.Canonical`. |
| `schema_version` | Целое число версии структуры; несовместимое изменение требует новой версии и мигратора. |
| `format_version` | Версия выпуска формата. |
| `generated_at` | Время формирования документа в ISO-8601. |
| `source` | Тип и имя источника; версия релиза указывается, если применима. Допустимые типы: `official_catalog`, `local_db`, `import_ascii`, `import_idf`. |
| `symbols` | Массив записей символов; `symbol_code` уникален в документе и используется для сопоставления при обмене. |

Запись Canonical включает `symbol_code`, имя и описание, `group_key`, `subgroup_key`, происхождение, `iso_behavior`, `last_change`, геометрию и коннекторы. `lifecycle_status` — необязательное обратно совместимое поле Canonical v1; новый экспорт должен его записывать, а при импорте записи без этого поля присваивается `draft`. В `origin.kind` различаются источники `standard` и `project`; это не заменяет `origin_type` из таблицы атрибутов раздела 8. Системные сведения о синхронизации помещаются в `versioning`. Расширение обратно совместимыми полями повышает `format_version`; изменение структуры или смысла обязательных полей повышает `schema_version`.

Геометрия Canonical представляется в декартовой системе координат с началом в центре символа сегментами `line`, `arc`, `polyline`, `polygon` или `ellipse`, областями заливки/штриховки и явными коннекторами `arrive`, `leave`, `tee` и `spindle`. Единица координат указывается в `geometry.units`; для Canonical v1 используется `mm`. Координаты нормализуются до трёх знаков после запятой. Payload hash рассчитывается как `sha256:` + SHA256 от нормализованного JSON с сортировкой ключей; в hash входят геометрия, области и атрибуты записи.

Словесное `iso_behavior.user_can_edit` является представлением разрешения редактирования, заданного атрибутом `is_user_modified`; это не признак того, что локальная правка уже произошла. Для правил конфликтов используется происхождение `forked_official`. Числовые значения legacy-атрибутов хранятся отдельно в `attributes` и остаются авторитетными для обратного экспорта; boolean-поля `iso_behavior` не заменяют эти коды.

`last_change.date` и `last_change.reason` описывают последнее изменение. При импорте событием изменения считается импорт, а при переносе исторической записи — миграция; дата не должна выдаваться за исходную дату создания символа. `versioning` содержит upstream-версию, локальную ревизию, payload hash, последний синхронизированный релиз и `sync_state`. Флаг фактического локального расхождения, если он присутствует в Canonical, называется `has_local_changes` и не подменяет `is_user_modified`.

## 9.3 Human-Readable Symbol

Текущий человекочитаемый формат `OpenIso.Symbol.HR` имеет `schema_version=2` и описывает один символ в оболочке `format`, `schema_version`, `symbol`. В записи символа используются код, имя, описание, группа, подгруппа, статус, единицы, начало локальной системы координат, классификация, коннекторы, примитивы, стили и метаданные. Новый символ по умолчанию имеет `lifecycle_status=draft`.

Система координат HR — декартова 2D; единица по умолчанию — `mm`, начало задаётся в `symbol.origin`, допускаются отрицательные координаты. Рекомендуемая точность координат — три знака после запятой. Допускаются трансформации примитивов `translate`, `rotate`, `scale`; перед сохранением Canonical v1 трансформации применяются к геометрии. Формат HR v2 не использует кривые Безье.

Допустимые примитивы: линия, дуга, ломаная, многоугольник и эллипс; слои: `body`, `axis`, `annotation`, `debug`. Примитив имеет уникальный в пределах символа ID, слой, данные геометрии и при необходимости ссылку на стиль. Стили задают параметры линии и заливки. Коннектор содержит тип, координаты и, если известны, направление, обязательность и метаданные; HR дополнительно допускает вспомогательный тип `aux`. Классификация может включать PCF/IDF-идентификаторы, коды `orientation`, `draw_orientation`, `flow_arrow`, `dimensioned`, `tracing`, `insulation`, `flow_dependency`, `user_definable`, `is_user_modified`, `is_official`, шаблон SKEY, допустимые токены концов и параметры шаблона.

Шаблон SKEY задаётся через `code_pattern`; допустимые заполнительные токены включают `**`, `@` и `+`. Допустимые значения для `**` перечисляются в `end_condition_tokens`; числовые параметры шаблона задаются отдельно в `pattern_params`.

Проверка HR-записи должна подтверждать непустой и уникальный в наборе код, уникальные ID примитивов, допустимые типы коннекторов, конечные координаты и наличие хотя бы одного коннектора `arrive` или `leave`. Параметры `segments` и `bend_radius` шаблона должны находиться в диапазоне `1..9`. Для экспортируемого в IDF символа строгий режим запрещает неподдерживаемые целевым форматом примитивы. Отображаемые координаты `symbol.origin` являются началом локальной системы геометрии, а Canonical `origin` — сведениями о происхождении; эти поля не взаимозаменяемы.

В Canonical не переносятся стили и примитивы как непрозрачный blob: геометрия и коннекторы преобразуются в соответствующие сегменты и точки, стили — в параметры сегментов и областей. HR `symbol.origin` применяется как начало локальной системы координат; Canonical `origin` остаётся сведением об источнике.

## 9.4 Импорт ASCII и IDF

ASCII и IDF преобразуются сначала в Canonical-представление, затем в атрибуты каталога или рабочей базы. Источники указываются как `import_ascii` / `Intergraph ASCII` и `import_idf` / `AVEVA IDF` соответственно. Поля заголовка 501 маппятся следующим образом:

| Поле legacy-записи | Canonical-атрибут |
| --- | --- |
| `new_skey`, иначе `base_skey` | `symbol_code` |
| `orientation` | `attributes.orientation` с сохранением исходного числового кода |
| `flow_arrow` | `attributes.flow_arrow` с сохранением исходного числового кода |
| `dimensioned` | `attributes.dimensioned` с сохранением исходного числового кода |
| `spindle_skey` | `attributes.spindle_skey` |

Группа и подгруппа берутся из классификации источника, если она присутствует. Числовые значения legacy-записи сохраняются в `attributes` без потери исходного кода.

Для геометрических записей используются следующие legacy-действия:

| Pen action | Результат |
| --- | --- |
| `1` | Начальная точка или коннектор `arrive`; для соответствующего символа — `spindle`. |
| `2` | Сегмент `line`. |
| `3` | Коннектор `tee`. |
| `6` | Коннектор `spindle`. |

Эквивалентные данные ASCII и IDF после нормализации должны давать одинаковые код символа, геометрию и коннекторы с учётом допуска округления. Координаты нормализуются до трёх знаков. Масштаб и единицы исходного формата должны быть известны до преобразования; преобразователь не должен угадывать их по величине координат.

Ошибка одной записи не должна прекращать импорт остальных записей файла. Невалидная запись добавляется в результат ошибок импорта с указанием строки и причины.

## 9.5 Экспорт в ASCII и IDF

Экспортёр преобразует поддерживаемые Canonical-сегменты и коннекторы в legacy-записи по явной таблице соответствий. Словесные подписи атрибутов не заменяют числовые коды, требуемые IDF.

В режиме `strict` неподдерживаемый примитив приводит к явной ошибке экспорта с перечислением проблем. В режиме `compat` допустима аппроксимация только для типов, для которых такое преобразование определено и проверено. Точки arrive/leave/tee/spindle должны отображаться в соответствующие pen actions без эвристик при экспорте.

## 9.6 Синхронизация и конфликты

Для каждого символа синхронизация сравнивает код, версию upstream, hash payload, локальную ревизию, последнюю применённую версию и состояние синхронизации. Повторный запуск для того же релиза должен быть идемпотентным.

Правила обновления:

| Условие | Действие |
| --- | --- |
| Эталонная версия новее, локального fork нет | Обновить рабочее представление символа; установить `sync_state=synced` и обновить последнюю применённую версию. |
| Версия и hash эталона не изменились | Не изменять локальную запись. |
| Символ имеет `origin_type=forked_official`, а эталон изменился | Не перезаписывать локальные атрибуты; сохранить upstream-версию и отметить `sync_state=conflict`. |
| Эталонный каталог удалил символ | Не удалять локальную запись автоматически; пометить `sync_state=deprecated_upstream`. |
| Символ создан локально и отсутствует в эталонном каталоге | Сохранить его локально; не заменять запись совпадающего имени автоматически. |

Ручное разрешение конфликта поддерживает две операции:

1. **Принять эталон:** заменить локальные атрибуты эталонными, увеличить локальную ревизию, обновить последнюю применённую upstream-версию и установить `synced`.
2. **Оставить локальную версию:** сохранить локальные атрибуты, увеличить локальную ревизию, отметить upstream-версию как обработанную и установить `synced`.

После синхронизации код символа остаётся уникальным, hash соответствует payload, а `sync_state` принадлежит перечислению `synced`, `conflict`, `upstream_newer`, `deprecated_upstream`. Разрешение конфликта и автоматическое обновление не меняют `lifecycle_status` без отдельного действия пользователя.

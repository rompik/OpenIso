# 22. Термины и сокращения

Этот раздел поясняет сокращения и термины, используемые в спецификации. Он служит справочником и не заменяет требования тематических разделов. Если полная расшифровка названия не установлена спецификацией, это указано отдельно; догадка не считается утверждённым требованием.

## 22.1 Сокращения и названия

| Термин | Расшифровка или значение |
| --- | --- |
| `ASCII` | American Standard Code for Information Interchange. В спецификации — также обозначение legacy-формата файлов символов Intergraph, а не только кодировки текста. |
| `CAD` | Computer-Aided Design — система автоматизированного проектирования. |
| `ER` | Entity–Relationship — модель «сущность — связь» для описания структуры данных. |
| `.exe` | Исполняемый файл Windows; standalone-сборка приложения распространяется в этом формате. |
| `GUI` | Graphical User Interface — графический пользовательский интерфейс. |
| `HR` | Human-Readable — человекочитаемый формат `OpenIso.Symbol.HR`. |
| `IDF` | Формат обмена символами, обозначенный в спецификации как формат AVEVA. Полная расшифровка сокращения в проекте не задана. |
| `ISOGEN` | Название внешней системы или стандарта, с которым связаны атрибуты символа. Полная расшифровка в спецификации не задана. |
| `JSON` | JavaScript Object Notation — текстовый формат структурированных данных. |
| `JSON Schema` | Формат описания структуры JSON-документа и проверки его соответствия этой структуре. |
| `MIT` | Название используемой в проекте открытой лицензии; это не расшифровываемое в спецификации сокращение. |
| `OIS` | Часть обозначения формата `openiso-ois` для экспорта и резервной копии локального состояния. Расшифровка названия не задана. |
| `ORM` | Object-Relational Mapping — сопоставление объектов и реляционных таблиц; ORM — библиотека или слой, реализующий такое сопоставление. |
| `PCF` | Формат или область обмена, для которой предусмотрен атрибут `pcf_identification`. Полная расшифровка в спецификации не задана. |
| `PyPI` | Python Package Index — индекс пакетов Python. |
| `SHA-256` | Криптографическая хеш-функция, формирующая 256-битное значение; используется для контрольной суммы payload. |
| `SKEY` | Symbol Key — код типа символа трубопроводного компонента. |
| `SQL` | Structured Query Language — язык запросов к реляционным базам данных. |
| `SQLite` | Встраиваемая реляционная база данных; `sqlite3` — стандартный модуль Python для работы с ней. |
| `UI` | User Interface — пользовательский интерфейс. `GUI` — его графический вариант. |
| `UUID` | Universally Unique Identifier — универсальный уникальный идентификатор. Вопрос о его применении дополнительно к коду SKEY не решён; см. раздел 19. |
| `ISO-8601` | Международный стандарт представления даты и времени; в спецификации задаёт формат временных меток. |

Названия `AVEVA`, `Intergraph` и `IsoAlgo` используются как имена компаний, систем или продуктов, а не как сокращения с расшифровкой в этой спецификации.

## 22.2 Форматы и источники данных

| Термин | Значение в спецификации |
| --- | --- |
| `OpenIso.json` | Эталонный каталог символов. Это источник определений, а не формат промежуточного обмена. |
| `OpenIso.Canonical` / Canonical | Определённый проектом версионируемый JSON-формат обмена. В нём нормализуются символы, атрибуты и геометрия при преобразовании между каталогом, хранилищем и форматами импорта/экспорта. Canonical не является эталонным каталогом. |
| `OpenIso.Symbol.HR` / Human-Readable | Человекочитаемый входной формат для описания, проектирования и ревью одного символа. После проверки его данные могут быть импортированы в эталонный каталог. |
| `openiso-ois` | Формат экспорта или резервной копии локального состояния. Он не заменяет `OpenIso.json` как источник эталонных определений. |
| Legacy-формат | Ранее существующий внешний формат обмена, который OpenIso продолжает поддерживать, например ASCII Intergraph или IDF AVEVA. |
| Эталонный каталог | Авторитетный набор определений символов. В текущей спецификации эту роль выполняет `OpenIso.json`. |
| JSON Schema | Машинно-проверяемый контракт структуры документа. Конкретные схемы и примеры перечислены в разделе 9. |

## 22.3 Модель символа и синхронизация

| Термин | Значение в спецификации |
| --- | --- |
| Код SKEY (`symbol_code`, `name`) | Читаемый код символа, используемый для его идентификации в каталогах и обменных документах. В текущей модели он не заменён UUID. |
| Геометрический примитив | Элемент графики символа, например линия, дуга, ломаная, многоугольник или эллипс. |
| Коннектор | Точка соединения символа с трубопроводом или другим элементом; типы Canonical включают `arrive`, `leave`, `tee` и `spindle`. |
| `schema_version` | Версия структуры документа. Изменение структуры или смысла обязательных полей требует новой версии схемы. |
| `format_version` | Версия выпуска формата; применяется для обратно совместимых расширений. |
| Payload | Данные символа, используемые для обмена или сравнения; в Canonical hash payload учитывает геометрию, области и атрибуты. |
| Payload hash | Контрольная сумма данных символа. Используется, чтобы обнаруживать изменения содержимого; это не идентификатор символа. |
| Upstream | Эталонная версия или каталог, с которым сравнивается локальная запись. Термин сам по себе не означает получение данных по сети. |
| Fork (`forked_official`) | Локальный вариант официального символа. Его локальные изменения нельзя автоматически заменять обновлением эталона. |
| Локальная ревизия (`local_revision`) | Номер последовательного изменения локальной записи символа. |
| `source_type` | Классификация источника данных, например `standard`, `company` или `project`. |
| `origin_type` | Происхождение записи, например `user`, `official`, `forked_official` или `imported`. Это отдельное свойство, не тождественное `source_type`. |
| `origin.kind` | Поле происхождения символа в Canonical, например `standard` или `project`; его нельзя автоматически отождествлять с `origin_type`. |
| `lifecycle_status` | Состояние готовности символа, например `draft`, `in_review` или `approved`; оно не обозначает происхождение или состояние синхронизации. |
| `is_user_modified` | Разрешение пользователю изменять символ по правилам ISOGEN, а не признак того, что локальное изменение уже произошло. |
| `sync_state` | Состояние согласования локальной записи с эталонной версией, например `synced` или `conflict`. |
| Round-trip | Цикл преобразования данных из одного формата в другой и обратно с проверкой сохранения поддерживаемых значений. |
| Идемпотентность | Свойство операции, при котором повторный запуск с теми же входными данными не создаёт дополнительных изменений. |

Для атрибутов символа, их хранения, форматов и правил преобразования нормативными остаются разделы 8 и 9. Раздел 19 содержит открытые решения, в том числе вопросы о UUID и точном соответствии некоторых legacy-значений полям Canonical.

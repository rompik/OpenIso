# План обновления базы данных простыми словами

Дата старта: 2026-04-22
Ответственный: команда OpenIso

## Зачем мы это делаем
Сейчас данные о символах хранятся и обновляются так, что добавлять новые форматы и безопасно обновлять каталог сложно.

Наша цель: сделать систему понятной и стабильной для инженера, чтобы:
- символы можно было импортировать и экспортировать без ручных обходных путей;
- обновления официального каталога не затирали пользовательские правки;
- любую ошибку можно было отследить и восстановить.

## Что должно получиться в итоге
- [ ] Есть единая, понятная структура данных для всех форматов.
- [ ] Обновления базы проходят по шагам и с журналом, без ручного редактирования.
- [ ] Новый формат можно подключить без переделки всего приложения.
- [ ] Проверки на тестах подтверждают, что импорт и экспорт не ломаются.

## Какие проблемы закрываем
- [ ] Геометрия хранится в неудобном виде, из-за этого сложнее обмениваться данными.
- [ ] Логика импорта слишком зависит от текущих форматов.
- [ ] Плохо видно, откуда пришел символ и кто его менял.
- [ ] Часть изменений базы делается на лету, а не через контролируемые миграции.

## Как обновляется база при новом релизе

Простой принцип:
1. Приложение видит новую версию каталога.
2. Сравнивает каждый символ с локальной базой.
3. Если символ пользователь не менял, обновляет автоматически.
4. Если пользователь менял, ставит в конфликт и просит решение.
5. Локальные пользовательские символы не удаляет.

Статусы символа:
- synced: локальная версия синхронизирована.
- conflict: есть расхождение, нужно ручное решение.
- upstream_newer: в каталоге версия новее, локальный символ не перезаписываем.
- deprecated_upstream: символ убран из официального каталога, но локально сохранен.

## Основные риски и защита
- Риск: старая пользовательская база не откроется.
  Защита: автоматическая резервная копия перед миграцией.

- Риск: геометрия в новом формате будет отличаться от старого.
  Защита: сравнение по эталонным файлам и round-trip тесты.

- Риск: переход затянется из-за поддержки двух путей.
  Защита: поэтапный rollout и feature-flag.

## Минимум полей для первого шага миграции

Для безопасного старта достаточно добавить:
- origin_type (происхождение символа)
- upstream_symbol_code (код в официальном каталоге)
- upstream_symbol_version (версия из каталога)
- upstream_payload_hash (контрольная сумма содержимого)
- is_user_modified (признак локальной правки)
- local_revision (локальная ревизия)
- last_synced_release_version (последний синхронизированный релиз)

Этого достаточно, чтобы:
- не терять пользовательские правки;
- безопасно обновлять официальный каталог;
- видеть и разбирать конфликты.
